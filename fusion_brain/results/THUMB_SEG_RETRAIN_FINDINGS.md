# Layer 3 follow-up: U-Net retrained on seeded flash-diff labels (round 45's own root-cause fix)

## Background

Round 45 (layer 3, masking) found the real cause of the U-Net's 31% (4/13)
real localization failure rate: its training labels were generated by
`ml/thumb_seg/build_dataset.py` calling `_segment_via_flash_diff` with NO
seed -- the pre-round-16 frame-centre default. The model was distilled from
a detector aimed at the wrong point. This round executes the root-cause fix
(retrain on correctly-seeded labels) rather than the inference-time patch
already built and held off (`_UNET_GUIDE_SEED_ENABLED`).

## What was built

1. **`build_dataset.py` fixed**: now fetches each capture's real
   `guideRegion` and seeds `_segment_via_flash_diff(amb, fl, ksize,
   seed_cx=guideRegion.cx*w, seed_cy=guideRegion.cy*h)`, matching the exact
   formula `afis_print._flash_diff_mask` already uses in production. Falls
   back to unseeded only when a capture genuinely has no `guideRegion`
   (0/107 real captures used needed the fallback).
2. **Dataset regenerated**: 107 real captures, 305 successfully-segmented
   flash-diff pairs, 610 training images. Spot-checked 6 random labels
   visually against the raw photos before training -- all 6 correctly land
   on the pad, zero gross mislocations (two have minor boundary
   imperfections: one under-covers near the tip, one has a ragged edge
   against a low-contrast striped background, neither touches background).
3. **Retrained on real SageMaker GPU** (`ml.g4dn.xlarge`, af-south-1, same
   architecture/hyperparameters as the existing model, no tuning): full 80
   epochs, clean monotonic descent, best val loss 0.1693 (epoch 64).
   Checkpoint: `s3://clearbridge-fingerprint-training-085068687041-af-south1
   -an/thumb-seg-unet-seeded-2026-08-29-12-10-42-639/output/model.tar.gz`.
   Real billable cost: ~$2.17 (a first, shorter attempt that hit a 1h time
   cap cost an additional ~$1, both real and modest).
4. **Exported to ONNX**, verified against the exact I/O contract
   `sfm_pipeline._segment_via_ml_model`/`afis_print._unet_mask` expect
   (input `(1,1,256,256)` float32 named `input`, output float32 logits
   named `logits`) -- a drop-in replacement for `/tmp/thumb_seg_unet.onnx`.

## Real A/B test 1: localization (primary gate)

Same 24-capture population and `_unet_mask` code path round 45 measured,
`guide_region=None` matching production's real `_UNET_GUIDE_SEED_ENABLED
=False` (isolates the retrain's own effect from the separate, still-held
inference-time patch).

| | fail rate |
|---|---|
| OLD (production) model | 8/24 (33%) |
| **NEW (seeded-label retrain)** | **3/24 (12%)** |

**Zero regressions** -- every capture the old model localized correctly,
the new model still does. **5 of 8 previously-failing captures fixed**
(`a262d2b3`, `4ae6d13c`, `80a994ca`, `8ed1c600`, `f4cb3ba5`).

On the 4 specific known failures the spec named:

| capture | OLD | NEW |
|---|---|---|
| `4ae6d13c` | fail (5.5% overlap) | **fixed (84.1%)** |
| `80a994ca` | fail (22.8%) | **fixed (84.7%)** |
| `474b4d6a` | fail (0% -- wrong blob) | still fails (no detection at all) |
| `1d186afc` | fail (16.9% -- wrong blob) | still fails (no detection at all) |

2/4, not the spec's stated 0/13 target. Real, substantial, safe -- not
complete. `1cc301a8` (already failing under the old model via the OPPOSITE
mechanism, over-segmentation) still fails under the new model, but now via
under-detection instead -- not a new failure, but a changed failure mode
worth knowing about.

## Real A/B test 2: end-to-end NFIQ2 (secondary, per the spec)

Same 13 captures that actually route to the U-Net in real production
(flash-diff unavailable/fails), through the real `generate()` pipeline,
old vs new checkpoint.

**Mean delta: -2.46. 3 better / 7 worse / 3 tied.** Two real, larger
regressions: `1c019820` -14, `eacb0b2c` -18. Both localization-fixed
captures (`4ae6d13c`, `80a994ca`) scored LOWER NFIQ2 despite objectively
better mask placement (-6, -2) -- the same NFIQ2-doesn't-reward-fidelity
pattern layers 3/4/5 of this architecture pass already found independently,
now confirmed a fourth time on a genuinely different mechanism (a retrained
detector, not a measurement-restriction flag).

## Real A/B test 3: matchability (SourceAFIS, not NFIQ2) -- found a real false-match risk

CTO asked directly to test matchability rather than trust NFIQ2 alone, per
this project's own standing prime directive. Two real genuine cross-session
pairs exist inside the 13-capture unet-routed population itself (same
`userId`, two real captures each): `4ae6d13c` x `5363a49b` (one of the
localization-fixed captures) and `1d186afc` x `b615f37b` (`1d186afc` is one
of the two still-failing captures). Rendered each capture's best-of-
variant-pool print under old/new, scored genuine pairs and an 8-capture
real impostor pool via SourceAFIS.

**Genuine scores stay in the noise floor either way** -- neither pair gets
close to SourceAFIS's own ~40 "reliable match" guidance, old or new
(`4ae6d13c`x`5363a49b`: 0.62 -> 0.71; `1d186afc`x`b615f37b`: 0.00 -> 9.74,
a real increase but still far below a genuine match).

**The real finding is a false-match risk, not a genuine-match gain.**
`b615f37b`'s impostor max jumped **2.14 -> 71.55** -- nearly 2x SourceAFIS's
own recommended threshold -- against ONE specific real impostor
(`01662ffb`). Isolated and visually confirmed: these are two clearly
different real fingers (different core/delta placement, different overall
pattern), yet the new model's rendering of `b615f37b` scores as a strong
match against an unrelated identity. `b615f37b` was not even one of the
localization-fixed captures -- its mask was already correctly accepted
under both models -- but swapping the U-Net changed which variant wins
selection for it (`fuseMaxc`@74 old -> `freqNorm`@60 new), and that
different print carries real cross-identity false-match risk. The other
two test captures' impostor risk moved only mildly (2.26->3.51, 2.56->3.85,
both still low).

Same 4 captures' full-variant-pool NFIQ2 (a partial correction to test 2
above, which only used the plain `native` variant): `4ae6d13c` 67->64,
`5363a49b` 67->79, `1d186afc` 68->68, `b615f37b` 74->60 -- confirms test 2's
own native-only numbers understated what's achievable per capture, but
doesn't change the verdict below.

## Decision: HOLD, do not move toward production -- a real false-match risk, not just a quality-metric wash

The false-match finding is more serious than the NFIQ2 result alone would
have suggested, and on its own is sufficient reason not to move this
checkpoint toward production: a biometric identity system trading a
mis-location fix for even one real cross-identity false-match risk is the
wrong trade, independent of whether NFIQ2 nets positive or negative. This
needs a real fix (more training data, a different loss, or evaluating a
wider set of genuine/impostor pairs to know how common this is) before
being reconsidered, not just a stronger scanner reference.

Per the spec's own stated bar ("if it's 0/13... conditionally shippable" --
we got 2/4 named, 5/8 overall) and the real net-negative NFIQ2 result, this
does not cross into "ship it" on the only downstream metric currently
available. This is real, useful progress -- a correctly-seeded dataset, a
retrained checkpoint, and a validated, safe (zero-regression) localization
improvement -- but it sits in exactly the same place as every other
correctness-improving fix in this pass: waiting on the real ≥500-DPI
scanner reference to know whether the localization gain is a genuine
matchability win NFIQ2 can't see, or whether the two large individual
regressions (`1c019820`, `eacb0b2c`) are real costs.

**Artifacts preserved for whenever that reference lands**: retrained
checkpoint (`best.pt`, epoch 64) and exported ONNX are local
(`/tmp/thumb_seg_unet_seeded.onnx`, not committed -- gitignored per this
project's own convention for model binaries); the S3 checkpoint persists
independently. `build_dataset.py`'s fix, the SageMaker launcher, the ONNX
exporter, and both A/B scripts are all committed and reusable.
